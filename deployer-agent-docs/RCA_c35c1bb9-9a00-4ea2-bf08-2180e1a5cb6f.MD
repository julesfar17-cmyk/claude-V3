# RCA — BeatCut (pro-mailer-2) — Cloudflare « could not parse » intermittent au login

## Verdict
**Le pod backend production est tué en boucle par le kernel pour dépassement mémoire (OOMKilled, exit 137).** Chaque kill coupe les requêtes en cours de traitement → réponse vide/tronquée à l'origine → Cloudflare renvoie « The origin web server sent a response that Cloudflare could not parse » (type 520/502). C'est un problème de **RESSOURCES (tier)**, PAS le code de login, PAS le keep-alive uvicorn.

## Preuves (production, run c35c1bb9-9a00-4ea2-bf08-2180e1a5cb6f, cluster target-2)

### 1. OOMKilled répété — get_pod_events
- Pod `r-...-fzbl7`, container : `last_termination = OOMKilled, exit_code 137, finished 2026-08-15T09:07:42Z`, **restart_count = 13**.
- 2e pod `r-...-lhdmc` : mêmes BackOff / probes échouées.
- Événements corrélés au kill (signature exacte d'une réponse coupée en plein vol) :
  - `Liveness probe failed: ... read: connection reset by peer` (08:50:53)
  - `Liveness probe failed: ... context deadline exceeded (while awaiting headers)` (×4)
  - `Startup probe failed: ... connect: connection refused` (×79) → le container redémarre.
  - `Liveness probe failed: HTTP probe failed with statuscode: 503` → backend down.
  - `BackOff restarting failed container` (×25).

### 2. Redémarrages uvicorn visibles dans les logs applicatifs
`Application startup complete` / `Uvicorn running on http://0.0.0.0:8001` apparaissent plusieurs fois (≈09:05, ≈09:13) — le process meurt et redémarre à répétition. Un `POST /api/auth/login 200 OK` juste après un redémarrage confirme que le login lui-même est sain ; il échoue seulement quand le kill survient pendant la requête.

### 3. Tier / limites — get_tier
- Tier actuel : **tier_0 « Starter »** — `memory: 200Mi (request)`, **`memory_limit: 512Mi`**, `cpu_limit: 250m`, 2 replicas, HPA/VPA désactivés.
- 512Mi est très insuffisant pour cette app : transcodage FFmpeg (proxies vidéo/exports), stockage vidéo GridFS (scan de 3215 fichiers), et endpoints admin Stripe qui bouclent sur TOUTES les charges/subscriptions (`limit=100` paginé). Un pic pendant un transcodage dépasse 512Mi → OOM.

## Pourquoi le monkey-patch keep-alive n'a rien changé
`_bump_uvicorn_keepalive()` (120s) traite une **course sur connexion idle** réutilisée. Ici la réponse vide vient de la **mort du process (OOM)**, pas d'une fermeture keep-alive. Le patch est un faux-piste ; il peut être retiré. La corrélation « par moment » = fenêtre du kill/redémarrage, pas un pattern keep-alive.

## Correctif à appliquer

### PRIORITÉ 1 — Infra (résout le symptôme immédiatement) — action utilisateur
Monter le tier via **Deployment Panel → Resources**. tier_0 = 512Mi est le plafond qui saute.
Recommandation : au minimum **tier_2 « Grow »**, idéalement **tier_3 « Scale »** vu FFmpeg. Objectif : que la limite mémoire couvre le pic transcodage + serving concurrent sans jamais atteindre le plafond (plus de exit 137).

### PRIORITÉ 2 — Code (réduire l'empreinte mémoire, empêche la récidive) — pour E1/le dev
1. **Sortir le transcodage FFmpeg du pod qui sert les requêtes** (worker/tâche de fond dédiée) pour qu'un pic transcodage ne puisse plus tuer le pod servant les logins.
2. **FFmpeg en flux disque, pas en RAM** : lire/écrire via l'ephemeral storage (1Gi dispo) plutôt que buffers mémoire/GridFS ; limiter threads/résolution/preset.
3. **Endpoints admin Stripe** (`/api/admin/stats`, `/api/admin/payments/*`) : ils chargent toutes les charges/subscriptions en mémoire (boucles `limit=100`). Paginer/streamer/cacher.
4. **Retirer le monkey-patch keep-alive** (non pertinent à ce bug).

## Note secondaire (non lié au 520)
Warnings répétés `Mux upload create 400 : Free plan is limited to 10 assets` — quota Mux atteint, à traiter séparément (n'a pas de rapport avec l'erreur Cloudflare).

## Statut
Diagnostiqué à partir des logs/événements de prod (OOMKilled exit 137, restart_count=13, limite 512Mi). **Non reproduit en sandbox** : classe ressources/charge live (FFmpeg + DB), non reproductible sans secrets ni charge réelle. Le run de déploiement est « success » — l'app est saine ; le défaut est un OOM runtime, pas un échec de build/deploy.
